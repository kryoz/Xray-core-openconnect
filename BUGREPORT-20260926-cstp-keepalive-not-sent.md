# BUG REPORT: CSTP keepalive/DPD не отправляются — idle-сессии умираают за NAT (CGNAT)

- Дата: 2026-09-26
- Компонент: `proxy/openconnect` (CSTP/TCP data path)
- Сборка: linux/amd64 static, sha256 `2ec7c256a675…` (рабочее дерево поверх 1f769e97 + правки
  per-user метрик 2026-09-26 17:38; dist `1d180a07` — тот же CSTP-код)
- Серьёзность: **высокая** — все клиенты за NAT без UDP (CGNAT/LTE, корпоративные сети)
  не могут держать сессию; split-маршрутизация не при чём.

## Симптом

Реальный клиент (Keenetic, встроенный openconnect; LTE + CGNAT, UDP зарезан → DTLS disabled)
подключается к Xray-openconnect, получает все split-маршруты и DNS, и **через ~51 секунды
простоя сессия умирает без единой ошибки в журнале сервера**, после чего клиент уходит в
цикл реконнектов (CONNECT → смерть → CONNECT). Тот же клиент против нативного ocserv
(keepalive=15) работает годами по тому же LTE-каналу.

## Доказательства

1. **Сервер не отправляет ничего при простое.**Loopback-сессия (openconnect 9.12, `--no-dtls`),
   30 секунд полного простоя, `tcpdump -i lo 'tcp port 8443'` → **0 пакетов**. При этом data-путь
   исправен: HTTP-флоу через туннель в split-назначение проходит (ответ 403 от CloudFront за 0.1с),
   DNS через туннель отвечает, сессия жива неограниченно долго (NAT нет).
2. **В коде нет отправителя.** `control.go:32 cstpKeepalive = 10` и заголовки
   `X-CSTP-Keepalive` / `X-CSTP-DPD` (control.go:298–299) — только декларация. DPD-машина
   (read-deadline → DPD_OUT → kick) реализована исключительно в `dtls.go:212–219` (UDP-путь).
   CSTP-путь (`acPKTKeepalive = 7` определён в dtls.go:24, но по TCP не отправляется никем).
3. **Тайминг смерти совпадает с CGNAT idle-таймаутом.** Журнал сервера: циклы
   CONNECT каждые ~51с (18:08:23 → 18:09:14 → 18:10:09 …), у клиента `IP address cleared`
   в течение ≤40с после успешного CONNECT с установленными маршрутами.

## Почему это блокер для миграции

Сайт-сценарий: 6 роутеров Keenetic (группа splitroute) сидят на LTE/CGNAT, UDP у оператора
зарезан (DTLS disabled и против ocserv тоже — occtl показывает `(no-dtls)`). Для них
единственный канал — CSTP over TCP, и его жизнеспособность при простое полностью зависит
от серверных keepalive. Пока таймера нет — эти клиенты неработоспособны на Xray.

## Просьба

1. Реализовать по CSTP то, что уже есть по DTLS (`dtls.go:212`), по образцу ocserv
   (`src/worker-vpn.c`, keepalive/DPD таймеры):
   - каждые `cstpKeepalive` сек простоя отправлять клиенту `AC_PKT_KEEPALIVE` (type 7);
   - по истечении `dpd` сек простоя — `AC_PKT_DPD_OUT` (type 3), при отсутствии
     `AC_PKT_DPD_RESP` (type 4) в течение ещё `dpd` сек — закрывать сессию.
   Значения брать из тех же настроек, что попадают в заголовки (конфиг `keepalive`/`dpd`).
2. (Опционально, замечено при диагностике) `X-CSTP-Split-Include` отправляются в порядке,
   обратном конфигурационному списку (первая route из groups приходит последей строкой).
   ocserv-совместимость не ломается, но порядок неожиданный — стоит проверить, где
   разворачивается слайс.
3. Собрать новый дист после фикса.

## Обходные пути (не решение)

- Держать NAT-клиентов без UDP на нативном ocserv до фикса.
- Включить TCP keepalive на уровне ядра для listener-сокета (`SetKeepAlive` +
  `SetKeepAlivePeriod` < NAT-таймаута) — хуже CSTP-фреймов (невидимо для клиента,
  не даёт DPD-семантики), но как горячий фикс спасает NAT-маппинг.

## Окружение

- gate: Debian 13, x86_64; xray-test.service, inbound oc-test 0.0.0.0:8443 (tcp+udp),
  пул 172.16.10.0/24, группы/split-маршруты (278 X-CSTP-Split-Include — парсинг клиентом
  корректен, все дошли).
- Клиент: Keenetic OS (OpenConnect-компонент), аплинк UsbQmi0 (LTE), local endpoint
  100.116.242.22 (CGNAT), DTLS disabled.
- Контраст: openconnect 9.12 loopback без NAT — сессия жива >45с в полном простое
  (подтверждает, что смерть — внешняя по отношению к серверу, триггер — молчащий канал).

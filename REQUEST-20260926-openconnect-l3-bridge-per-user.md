# Запрос: достижимость выбранных пользователей OpenConnect-inbound (клиент↔клиент в userspace; опционально kernel-мост)

**Дата:** 2026-09-26 (ревизия 2: приоритет — userspace-коммутация, kernel-мост — опция)
**Статус:** БЛОКЕР для перевода 6 роутер-пользователей прод-сервера networp gate
(и единственный способ вернуть доступ к LAN за роутерами).
**Сборка, на которой воспроизведено:** самосбор с дерева мейнтейнера
(2026-09-26 17:38, бинарник sha256 `2ec7c256a675…`, позже `c3ba292f…` с cstpPump),
inbound `proxy/openconnect` (стек gVisor, `ocDevice` в `stack.go`).

---

## 1. Суть

Inbound терминирует клиентские L4-сессии в userspace-стеке gVisor. Kernel-интерфейса
к пулу нет, поэтому:

* **host→клиент невозможен**: `ip route get 172.16.10.115` на gate уходит в default
  (ens3, к провайдеру); ICMP до виртуальных IP клиентов — 100% loss;
* **клиент↔клиент невозможен**: флоу клиента A к IP клиента B попадает в
  routing.Dispatcher → freedom → kernel — и тоже теряется (нет маршрута к пулу).

Работают только флоу, инициированные клиентом (DNS через unbound на 172.16.10.1 —
жив, потому что это L4-коннект клиента к хосту).

**Прод-инцидент 2026-09-26:** home-router (статический 172.16.10.115) переведён с
ocserv на inbound — и доступ к домашней LAN (192.168.0.149 за NAT роутера,
port-forward'ы на VPN-IP `home.vpn`) потерян полностью: ни с gate, ни с других
клиентов. У ocserv это работало через TUN-устройства `vpnsN` + kernel-маршруты
`172.16.10.X dev vpnsN` + FORWARD-цепочку.

Пока это не решено, переводить роутеры (половина парка) на inbound нельзя.

## 2. Предлагаемая семантика — ОПЦИЯ per-user, не поведение inbound по умолчанию

Запрос: достижимость только для явно выбранных пользователей; остальные
работают как сейчас (userspace-терминация, производительность и семантика
routing-правил Xray для них не меняются).

```json
"inbounds": [{
  "protocol": "openconnect",
  "settings": {
    "users": [
      { "name": "home-router", "ip": "172.16.10.115", "l3": true },
      { "name": "alex",        "ip": "172.16.10.2" }
    ]
  }
}]
```

(формулировка на усмотрение мейнтейнера — per-user флаг `l3` или отдельный
список `l3Users`.)

### 2.1. Основной запрос (приоритет): коммутация клиент↔клиент внутри ocDevice

Главный прод-сценарий — **доступ к VPN-адресу одного клиента с другого клиента**
(admin-ноут в VPN → `172.16.10.115:22` port-forward роутера → LAN за ним).
Клиент↔клиент решается в userspace, без kernel-устройств:

* в `ocDevice` все туннели уже собраны в `tunnels[virtIP]`;
* сейчас пакет клиента A с `dst = virtIP(B)` уходит в gVisor-стек →
  routing.Dispatcher → freedom → kernel (где маршрута к пулу нет) → теряется;
* предлагаем: в точке входа RX (`dispatchLoop`) если `dst ∈ tunnels` и **оба**
  пользователя помечены `l3` — ретрансляция пакета сразу в туннель владельца
  dst, минуя стек (чистый L3-ретранслятор; TCP/UDP/ICMP работают одинаково);
* изоляция сохраняется: непомеченные пары — как сейчас (стек+freedom),
  спуфинг src проверять как обычно.

Это закрывает сценарий и сейчас (обе стороны на :8443), и после cutover,
когда весь парк будет на inbound.

### 2.2. Опционально (фаза 2, если 2.1 недостаточно): kernel-мост host→клиент

Полная L3-семантика ocserv для host-инициированных флоу (ssh/ping с сервера
по обычному адресу без перечисления портов):

1. L3-пакеты пользователя попадают в kernel через TUN-устройство (одно на
   сессию, как `vpnsN` у ocserv, — или одно на inbound с userspace-диспетчером
   по dst; на выбор мейнтейнера);
2. при подключении — kernel-маршрут `172.16.10.X/32 dev <tun>`, при
   отключении/рестарте — удаление (без устаревших /32);
3. host→клиент решается ядром: `FORWARD -s/-d 172.16.10.0/24 ACCEPT` и
   `INPUT -i vpns+ ACCEPT` у нас уже есть.

**Именование устройств: `vpns*`** — существующие правила работают без правок.
**Коллизия на переходный период**: ocserv-прод и xray-тест работают параллельно
и оба создают `vpnsN` — нужно либо иное имя префикса на время параллельной
работы (например, `xocN`), либо резервирование диапазона номеров.

## 3. Что должно сохраниться / на что обратить внимание

Общее (2.1 и 2.2):

* **Stats**: per-user счётчики (uplink/downlink/online) должны работать одинаково
  для ретрансляции и терминации — мониторинг строится на
  `xray_user_traffic_bytes{user=...}` (expvar).
* **Изоляция/спуфинг**: src-адрес ретрансляции валидировать (пакет от клиента A
  с src ≠ virtIP(A) — дроп, как сейчас).

Только для 2.2 (kernel-мост):

* **MTU** — согласованно с существующим поведением: у ocserv TUN-устройства
  `vpnsN` поднимаются с mtu 1434 (`try-mtu-discovery = true`); фрагментация
  или drop на границе kernel-моста недопустимы.
* **Egress L3-пользователей идёт по kernel-маршрутам** (как у ocserv: ip rule
  `from 172.16.10.0/24 lookup 100` → AWG-туннель), а НЕ через freedom-inbound'а
  с `sockopt.interface`. Routing-правила Xray (наши geosite:ru-сплиты) на
  kernel-пользователей не действуют — ожидаемо, семантика ocserv.
  (Для 2.1 egress не меняется вообще.)
* **Права**: создание TUN требует CAP_NET_ADMIN (инстанс у нас root; просто
  зафиксировать в доке).
* **Статические IP** (`users[].ip`) обязательны для kernel-режима: /32-маршрут
  вешается на предсказуемый адрес (валидировать при старте). Для 2.1
  статика не обязательна (карта туннелей строится по факту), но желательна —
  у нас на ней DNS/port-forward'ы роутеров.
* **Перезапуск Xray**: устройства и маршруты не должны дублироваться
  (идемпотентно по имени) и должны подчищаться.

## 4. Критерии приёмки (проверим на тестовом инстансе :8443)

Для 2.1 (клиент↔клиент, основной):

1. Клиент A (`l3`) → `ssh 172.16.10.115` (клиент B, `l3`) — доходит до
   port-forward'а роутера; работает и TCP, и ICMP (ping A→B).
2. Пара без `l3` (или помечена только одна сторона) — как сейчас: до virtIP
   не доходит.
3. Userspace-клиенты: без регрессий (DNS 172.16.10.1, egress, статистика).
4. `xray_user_traffic_bytes` растёт у обеих сторон ретрансляции.

Для 2.2 (kernel-мост, опциональная фаза):

5. `ping 172.16.10.115` с gate — работает; `ping <userspace-юзер>` —
   по-прежнему нет (маршрута нет).
6. `ssh 172.16.10.115` с gate — доходит до port-forward'а роутера.
7. Отключение L3-клиента — /32-маршрут удалён; рестарт Xray — нет дублей
   устройств/маршрутов; на переходный период — нет коллизии имён с ocserv.
